## D1 段ごとの書式
- 各段に書式を作り、AIは基本的に**前の段の書式を読んで**次の作業に入る
- ねらい：段から段への受け渡しを楽にし、出戻りを減らして、全体の token 使用量を下げる

## D2 段の構成
- ①意図 → ②仕様 → ③計画 → ④実装 → ⑤検証 → ⑥記録・考察 → ⑦ローンチ
- ②から **2.5 検証項目・実運用の探索** に枝分かれし、実装を見ずに確かめ方を決めて⑤に渡す（→ D15 で出発点を③に変更）
- ⑤から直接戻るのは④（作り直し）と 2.5（確かめ方の手直し）
- ②に戻るのは⑥の考察を通るときだけ。2.5 を直す必要があるときも、②を通ってから直す（2.5 の中身は必ず②から作られる）

## D3 書式のファイル形式と、ずれの見張り
- どの段にも .md を作り、段によって .yaml／.json を併存させる
  - 理由：段ごとに、作業する側（人・AI・機械）が扱いやすい形を選べる
- ずれの見つけ方
  - Claude Code が書いたとき：書き終えた直後に hook で比べる
  - 手で直したとき：毎朝7時から3時間ごとに比べ、差分確認リストを作る
- 判断：人が1日2回（朝9〜10時と19時）、差分確認リストを見て判断する
- 夜のあいだに手で直された差分は仮に許容して進め、AIは**手で直したあとの版**に従う。夜は実装とテストに充て、仕様の決定（②・2.5 の承認）はしない
- 方針：仕様の段階で完璧なものは作れないので、スピードを優先する
- 崩れる条件
  1. 許容と書かれていない差分が1件以上ある
  2. 夜に仮に許容して進めた結果が、予想から30％以上外れる、または UI/UX を人が1件でも「だめ」と判断する

## D4 正本
- どの段も **.md が正本**。.yaml／.json は .md から自動で作る副本
- 副本を手で直すことは**防ぐ**
  - 理由：運用を簡素にし、議論だけ深めて何も進まない状態を避けるため
  - 防ぎ方（案）：副本は作るたびに読み取り専用にする／先頭に「自動生成・編集禁止。正本：〇〇.md」と書く／D3 の3時間ごとの比較を保険として残す
- 崩れる条件：この決定による弊害を、AIが1週間で20個記録したら考え直す（記録の場所は⑥の書式に作る）
- 「.md を正本にする理由」は未記入

## D22 夜の作業の進め方
- 夜は、作業包・検証項目ごとに進める。止めるのは問題のあった項目だけで、ほかの項目は次の4つをすべて満たせば進める

  2. 止まった項目に依存していない
  3. 仕様の決定（②・2.5 の承認）を含まない
  4. 取り返しのつかない操作の点検が要らないか、すべて pass（2.5 では、検査点の決定を含まない）
- 止まった項目は、理由と人に聞きたいこと（最大3問）を残し、朝の判断に回す。同時に進める上限（4個）は夜も守る

## D25 NAGARE と EDA の役割分担
- 案ア：作法・開発の方法（メソドロジー）はすべて NAGARE にまとめ、EDA のリポジトリは道具（ツールの実行）だけに特化する。ソフトウェアなど他の開発対象でも同じにする
- NAGARE は「芯（どの開発にも共通の流れ）」と「パック（開発対象ごとの作法。例：半導体パック、ソフトウェアパック）」に分ける。どちらも NAGARE に置く
- NAGARE と EDA は「約束（契約）」でつなぐ。約束には、規約のルール ID が両方で食い違っていないかを自動で確かめる仕組みを含める
- 理由：NAGARE を AI ドリブンな開発の方法のまとめにしたい。方法と道具を分ければ、それぞれを独立に改善できる
- 崩れる条件
  1. 開発対象の種類が増えるほど、管理するもの（パック）が増える。開発対象ごとに検討が要るのはそもそも承知のうえ。物差し：パックが8個を超えたら見直す
  2. 今の流れと相性の悪い開発対象があると、その開発の足を引っ張る。やってみないとわからず、慣れていないだけの可能性もある。開発対象ごとに、初期の段階で芯についてのフィードバックを求める。物差し：初期の段階で、1つの工程に5時間以上かかることが5回以上出たら
  3. この先の AI の性能しだいで、この前提そのものが崩れる（どの大きさのモデルなら成り立つかを考える。物差しは保留）
  4. 段階ごとに時間がかかり、競合に負ける。2 と同じく初期のフィードバックで見るほか、開発期間中に人が「赤信号」という緊急コードを出せる。物差し：今の作業や今の工程から次に進むのに、1週間以上かかったら
- 赤信号：人がいつでも出せる緊急コード。AI は開発中、このオプションがあることを常に示す（出したときに何が起きるかは未決）

## D26 半導体の工程に入る前の「理解の関所」の厳しさ
- 修正した案 D にする。どの関所でも、まず AI が図を使って説明し、人がそれを自分の言葉で言い直す。そのあと AI が抜けを指摘して補い、人が工程の項目を決める
  - その工程を初めて通るとき：B（説明 → 言い直し → AI の指摘に答え終わる → 決める）
  - 2回目以降で前回の言い直しが残っているとき：A（説明 → 言い直し → 決める。AI の指摘は参考）
  - わからなければ、何度でも AI の説明に戻れる
- 理由：内容が難しく、白紙から説明できるようになるまでに時間がかかる。だから AI のヘルプを常に入れて、理解と速さを両立させる
- 崩れる条件
  1. 1つの関所に10分以上かかることが、2回続いたら
  2. 言い直しが AI の説明をなぞるだけになり、確認クイズの正答率が90％を下回ったら
- 確信度：90％。根拠：導入した直後なので、基準を甘めに置いている。改善が進むにつれて基準を上げる
- 理解ノートと確認クイズ（講座の資料をもとにした個人のノート）は人の PC に置いたままにする。NAGARE からは置き場所だけを参照し、中身・原文・図は NAGARE に入れない
- 「2回目」は、作るもの（モジュール）と工程の両方が2回目のときだけ2回目と数える。新しいモジュールは、前に同じ工程を通っていても初めて（B）とする。A になるのは、同じものを同じ工程でやり直すとき（不合格で戻った、仕様を変えた など）
- 2回目以降（A）でも、決める前に必ず「前回から何を・なぜ・どのように変えるか」を確認する
- 数え方の理由：理解を促進して開発のスピードを上げながら、全体と詳細を確実に理解したい。時間をいくらでも使える AI は、この進め方に向いている
- 数え方の崩れる条件：トークン数が増えやすく、経済的に割に合わなくなる。物差し：Claude の週間使用量（％）が、関所を始めた時点から5％増えたら。同じアカウントを他の人も使っているため、他の人の使用分も入り、実際より早めに「崩れた」と出ることがある。このずれは承知のうえで採用する（トークン数を直接数える案は、週間使用量がトークン数で公開されていないため採らなかった）
