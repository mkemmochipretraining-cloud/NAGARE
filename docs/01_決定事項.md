# 決定事項（2026-11-14 時点）

← [README](../README.md)

## D1 段ごとの書式
- 各段に書式を作り、AIは基本的に**前の段の書式を読んで**次の作業に入る
- ねらい：段から段への受け渡しを楽にし、出戻りを減らして、全体の token 使用量を下げる

## D2 段の構成
- ①意図 → ②仕様 → ③計画 → ④実装 → ⑤検証 → ⑥記録・考察 → ⑦ローンチ
- ②から **2.5 検証項目・実運用の探索** に枝分かれし、実装を見ずに確かめ方を決めて⑤に渡す
- ⑤から直接戻るのは④（作り直し）と 2.5（確かめ方の手直し）
- ②に戻るのは⑥の考察を通るときだけ。2.5 を直す必要があるときも、②を通ってから直す（2.5 の中身は必ず②から作られる）

## D3 書式のファイル形式と、ずれの見張り
- どの段にも .md を作り、段によって .yaml／.json を併存させる
  - 理由：段ごとに、作業する側（人・AI・機械）が扱いやすい形を選べる
- ずれの見つけ方
  - Claude Code が書いたとき：書き終えた直後に hook で比べる
  - 手で直したとき：毎朝7時から3時間ごとに比べ、差分確認リストを作る
- 判断：人が1日2回（朝9〜10時と19時）、差分確認リストを見て判断する
- 夜のあいだに手で直された差分は仮に許容して進め、AIは**手で直したあとの版**に従う。夜は実装とテストに充て、仕様の決定（②・2.5 の承認）はしない
- 方針：仕様の段階で完璧なものは作れないので、スピードを優先する
- 崩れる条件
  1. 許容と書かれていない差分が1件以上ある
  2. 夜に仮に許容して進めた結果が、予想から30％以上外れる、または UI/UX を人が1件でも「だめ」と判断する

## D4 正本
- どの段も **.md が正本**。.yaml／.json は .md から自動で作る副本
- 副本を手で直すことは**防ぐ**
  - 理由：運用を簡素にし、議論だけ深めて何も進まない状態を避けるため
  - 防ぎ方（案）：副本は作るたびに読み取り専用にする／先頭に「自動生成・編集禁止。正本：〇〇.md」と書く／D3 の3時間ごとの比較を保険として残す
- 崩れる条件：この決定による弊害を、AIが1週間で20個記録したら考え直す（記録の場所は⑥の書式に作る）
- 「.md を正本にする理由」は未記入

## D5 エージェントの分け方
- 各段（①②2.5③④⑤⑥⑦）にそれぞれ専用のエージェントを作る
- 呼び名：2.5 は「検証項目エージェント」、⑤は「検証エージェント」

## D6 2.5 の独立
- 2.5 の検証項目エージェントは、設計物を**人の許可があるときだけ**読める
- 許可がなければ読めないことを、仕組み（エージェントごとの hook）で守る（指示文で禁じるだけにはしない）

## D7 実装物の読み込み
- ③計画・④実装・⑤検証・⑥記録・考察：実装物を**いつでも読める**
- ①意図・②仕様・⑦ローンチ・2.5 検証項目：**人の許可があるときだけ**読める（仕組みは hook）
- どの段でも、仕様の変更が要ると判断したら自分では直さず、⑥経由で人に上げる
- 注意（検討時の指摘）：②が実装を読むと、実装の前提が仕様を通って 2.5 に入る（回り道）。読む量が増えると token も増える

## D8 許可の出し方
- 許可制の4つ（①②⑦2.5）が実装物を読むときは、その都度人が判断する
- 理由：flow をまだ回しておらず、何が弊害になるかがはっきりしないため

## D9 ①意図の段
- 意図メモの欄は14個すべて残す（最終状態・受け入れるリスク・想定問答を含む）
- 「今の状態」は、数字か、番号付きの段階で書く
- 「やらないこと」は、プロジェクトの段階ごとの表にする
- 聞き手のAIは、1回に最大3問まで聞く
- 書式：[03_書式/01_意図メモ.md](03_書式/01_意図メモ.md)

## D10 ②仕様の段
- 仕様書の欄は11個すべて残す
- 要求は1文1件。あいまい語の禁止一覧を使う
- 合格基準は、できる限り数字にする。数字にできないものは定性的でもよいが、「はい／いいえで判定できる文」と「誰が判定するか」を必ず書く
- 「どうやって確かめるか」は②では書かず、2.5 に任せる
- 書式：[03_書式/02_仕様書.md](03_書式/02_仕様書.md)

## D11 2.5 検証項目の段
- 他業界の知見の採否
  - P1 検査点の種類（建設 ITP）：採用。どの項目を停止点・立会点・書類確認にするかは人が決める
  - P2 検証と妥当性確認を分ける（医療機器・航空宇宙）：採用
  - P3 使う人の間違いを洗い出す（医療機器）：採用
  - P5 攻める側の立場の項目を別枠で持つ（レッドチーム）：採用
  - P4 検証の道具そのものの確かめ（製薬）：2.5 には入れず、EDA リポジトリ（mkemmochipretraining-cloud/EDA_tools_and_AI-tools_run）で扱う。壊れた RTL などを入れたときに EDA ツールがどう動くかを確かめ、問題があれば直す
- 「重要」の判定基準 1〜4（安全・セキュリティ／チップ後に直せない／多くの要求が依存／受け入れるリスクの外）を採用
- 2.5 は妥当性確認のため①意図メモも読む
- 書式：[03_書式/2.5_検証項目.md](03_書式/2.5_検証項目.md)

## D12 ③計画の段
- 進め方：これ以降の段も、半導体業界の作法を土台にし、ほかの業界から半導体にまだない知見を候補として出し、人が採否を決める
- 半導体の作法の表（ブロックの階層で分ける／つながりを先に決める／段に沿って進める／凍結の時点を置く）を土台にする
- 作業包の大きさ：機能ブロックごと（後で変わる可能性あり）
- 他業界の知見
  - P6 段取りの確認（建設のラスト・プランナー方式）：採用。前提ごとに必須／任意を判定する
  - P7 余裕を最長ルートの最後にまとめる（クリティカルチェーン）：採用
  - P8 同時に進める作業の上限（かんばん）：採用。上限は4個
  - P9 着手してよい条件（Definition of Ready）：P6 と組み合わせて採用
  - P10 事前検死：形を変えて採用。計画の段階で「何をもって失敗とするか」「何でアラートを出すか」を決める
- 書式：[03_書式/03_計画書.md](03_書式/03_計画書.md)
