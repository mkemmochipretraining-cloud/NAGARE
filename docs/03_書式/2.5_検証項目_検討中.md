# 2.5 検証項目（検討中）

← [README](../../README.md)

> 状態：案。下の「人が決めること」の3つが決まったら、検証項目表の列とエージェントの動き方を確定する。

## 役目と要件（人が出した要件）
- 設計フローに入るエージェントとは**別のエージェント**（検証項目エージェント）
- 仕様書を読み、次の3つの出どころから検証項目を洗い出す
  - (a) 世の中の検証の作法（規格・業界の型）
  - (b) 仕様の各要求から導く項目
  - (c) そのプロジェクト特有の項目（現場・実運用）
- 全体検証と部分検証の両方を考え、その中で重要（クリティカル）な項目と方法を特定する
- 業界は**半導体設計を中心**にし、ほかの業界の知見で半導体業界にないものは提案として出す（採否は人が決める）
- 設計物は人の許可があるときだけ読める（D6・D8）

## 成果物の形
半導体でいう検証計画（vPlan）にあたる「検証項目表」。1行が1つの検証項目（VI-xxx）で、出どころ・対応する要求・部分か全体か・方法・重要かどうかの印を持つ。

## 土台：半導体設計の検証の作法（出どころ (a)）

eda01 のフローと、EDA コンソールのサインオフ5分類にそろえる。

| 区分 | 主な作法 | 部分／全体 |
|---|---|---|
| 書き方の検査 | lint（規約違反の検出） | 部分 |
| 動作の確認 | シミュレーション（cocotb）、ランダムな入力、網羅率（コード・機能） | 部分・全体 |
| 数学的な証明 | 形式検証（性質の証明、等価性の確認）。空振りの見張りを必ず付ける | 部分 |
| クロックの境目 | CDC、リセットの検査 | 部分 |
| 物理と時間 | 合成後の等価性、タイミング（STA）、DRC・LVS | 全体 |
| 適合試験 | 規格の公式テスト（例：riscv-arch-test） | 全体 |
| 実機 | FPGA での動作確認 | 全体 |

## ほかの業界からの提案（採否は未決）

| # | 知見 | 出どころの業界 | 2.5 での使い方 | Kekkai での例 |
|---|---|---|---|---|
| P1 | 検査点の種類（停止点・立会点・書類確認） | 建設の ITP | 検証項目ごとに「合格を誰が解除するまで次へ進めないか」を書く | 重要な形式検証は停止点にし、人が解除するまで⑦に進めない |
| P2 | 検証と妥当性確認を分ける | 医療機器・航空宇宙 | 「仕様どおりか（検証）」と「①の意図どおりか（妥当性確認）」を別の項目にする。そのため 2.5 は①も読む | 仕様どおり遮断できても、現場の運用で使えなければ①の最終状態は満たせない |
| P3 | 使う人の間違いを洗い出す | 医療機器（使いやすさの規格） | 実運用の場面で、使う人が設定や操作を間違えたときを検証項目にする | 運用者がルール設定を誤る、LOCK の掛け忘れ |
| P4 | 検証の道具そのものを先に確かめる（据え付け・動作・実運用の3段の適格性確認） | 製薬 | 本番の検証の前に、道具の版、既知の正解と既知の誤りを正しく判定できるかを確かめる項目を置く | わざと壊した RTL を入れて、テストが不合格を出すかを先に確かめる |
| P5 | 攻める側の立場で壊しに行く項目を別枠で持つ | 情報セキュリティのレッドチーム | 「仕様を守っているか」とは別に「どう壊せるか」の項目を立てる | 監視をすり抜ける命令の並びを、攻撃者の立場で探す |

わざと誤りを入れてテストの強さを測る手法や故障注入は、半導体（特に車載）ですでに使われているので外した。

## 「重要（クリティカル）」の判定基準（案）
次のどれかに当てはまる項目に「重要」の印を付ける。
1. 安全やセキュリティに関わる
2. チップにしたあとでは直せない
3. 多くの要求がその項目に依存している
4. ①の「受け入れるリスク」の外にある
