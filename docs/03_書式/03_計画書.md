# ③計画書の書式（確定・D12）

← [README](../../README.md)

## 役目
②仕様を、④のAIに渡す**作業包（WP）**に分け、順番を決める。

## 土台：半導体設計の計画の作法
| 作法 | 中身 | ③での形 |
|---|---|---|
| ブロックの階層で分ける | チップ → ブロック → 部品の順に分ける | 作業包は**機能ブロック**の単位にする |
| つながりを先に決める | ポート・バス・レジスタの配置を、中身より先に固める | つながりを決める作業包を最初に置く |
| 段に沿って進める | lint → シミュレーション → 形式検証 → 合成 → … | 作業包ごとに、どの段まで通すかを書く |
| 凍結の時点を置く | 「RTL 凍結」のように、ここからは変えない時点を決める | ⑦に向けた凍結の時点を書く |

## 採用した他業界の知見
| # | 知見 | 出どころの業界 | 書式での形 |
|---|---|---|---|
| P6 | 段取りが済んだ作業だけを約束する（ラスト・プランナー方式） | 建設（リーン建設） | 作業包ごとに、前提が**必須**（そろわないと着手できない）か**任意**（そろわなくても着手してよい）かを判定する |
| P7 | 余裕を最長ルートの最後にまとめて持つ（クリティカルチェーン） | 製造・プロジェクト管理 | 作業包の見積もりには余裕を入れず、「5. まとめた余裕」に置く |
| P8 | 同時に進める作業の上限（かんばんの仕掛かり上限） | 製造（トヨタ） | ④が同時に手を付けてよい作業包は **4個まで** |
| P9 | 着手してよい条件（Definition of Ready） | ソフトのアジャイル開発 | P6 と組み合わせ、作業包ごとの「着手の条件」の欄に前提ごとの必須／任意を書く |
| P10 | 失敗とアラートの条件を先に決める（事前検死を変形） | 意思決定の研究 | 「7. 失敗とアラートの条件」の表 |

## 作業包の大きさ
- 単位は**機能ブロックごと**
- 後で変わる可能性あり。⑥の考察で、ブロックの大きさのばらつきが問題になっていないかを見る

## 計画のAIの動き方
1. ②仕様が approved かを確かめる（入口）
2. 機能ブロックごとに作業包に分ける。つながり（ポート・バス・レジスタ）を決める作業包を最初に置く
3. ②のすべての要求が、どれかの作業包に入るまで分ける（100％ルール）
4. 依存関係から順番と最長ルートを出す
5. 作業包ごとに、前提の必須／任意を判定する
6. 見積もりには余裕を入れず、余裕は最長ルートの最後にまとめる
7. 失敗とアラートの条件を決める。決めきれない点は人に聞く（1回に最大3問）
8. 草案 → 出口の条件 → 人の承認 → ④へ（同時に渡すのは4個まで。着手の条件の必須がそろったものから）

## 10. 出口の条件（機械で判定）
- [ ] 前の段（SPEC）が approved
- [ ] ②のすべての要求が、どれかの作業包に入っている
- [ ] どの作業包も、②の範囲の外のものを作っていない
- [ ] すべての作業包に機能ブロックと通す段が書かれている
- [ ] すべての前提に必須／任意が書かれている
- [ ] 依存関係に輪（循環）がない
- [ ] 最長ルートが書かれている
- [ ] まとめた余裕の量が書かれている
- [ ] 失敗とアラートの条件が1つ以上あり、物差しとしきい値が書かれている

- [ ] 9 が「なし」、または承認者が先送りを認めている
- [ ] 「2.5 へ」の申し送りに、ブロック分けと要求の対応以外のこと（設計物の場所・実装の手がかり）が書かれていない
- [ ] status が approved で、approved_by が埋まっている
