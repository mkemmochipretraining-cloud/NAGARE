# ⑥記録・考察の書式（確定・D20）

← [README](../../README.md)

## 役目
flow 全体の振り返りと、学びの集約場所。
1. 結果を記録し、物差し（token・出戻り・判断時間）を測る
2. 学んだことを、書式・規約・分類の判断基準に戻し、flow そのものの改善を NAGARE にフィードバックする
3. どの段からでも上がってくる「仕様を変える必要がある」を人に上げ、②に戻す（D2・D7）

## 土台：半導体設計の振り返りの作法
| 作法 | ⑥での形 |
|---|---|
| バグの記録 | ⑤の不合格を、分類（D18）ごとに集計する |
| 取り逃がしの分析 | 不合格ごとに「本来見つかるべきだった段」を書く |
| 網羅の穴の振り返り | ⑤の網羅率の結果から、穴を一覧にする |
| 正誤表 | 特採（P16）したものを⑦へ申し送る |

## 採用した他業界の知見
| # | 知見 | 出どころの業界 | 書式での形 |
|---|---|---|---|
| P20 | 4つの問いで振り返る（AAR） | 軍（米陸軍） | 「1. 振り返り」。「起きるはずだったこと」は①の最終状態と③の計画から持ってくる |
| P21 | 責めない振り返り | ソフト（Google SRE） | AIのエージェントの出来で片付けず、どの書式・規約・指示が足りなかったかを書く |
| P22 | ヒヤリハット | 航空・建設 | 常設の欄にはせず、AIが必要だと判断したときに随時提案する |
| P23 | 定期的な症例検討 | 医療（M&M カンファレンス） | 「頻度」の2段（週1回／全体の検証が3回回ったとき） |
| P24 | 横展開 | 製造（トヨタ） | 「7. 横展開」。flow そのものの改善は NAGARE へ（反映の仕方は B） |

## 頻度
| 振り返り | いつ | 中身 |
|---|---|---|
| 作業包ごと | 機能ブロックごとに毎回 | AAR の4欄、不合格と取り逃がし、計画との違い |
| 定期（週） | 週に1回 | その週の物差しの集計、弊害の件数、Andon fail の残り、無駄の許容線 |
| 全体 | 全体の検証が3回回ったとき | flow そのもの（書式・段の構成）とプロジェクト全体を見直し、NAGARE に反映する |

## 見直しのしきい値
- 弊害の記録：1週間で20個 → D4（.md 正本・副本の手直しを防ぐ）を見直す
- 無駄の許容線：夜に仮に許容して進めた作業のやり直しが週4回を超えた → D3（夜に進めるやり方）を見直す
- 2.5 の開始待ちが5日以上 → D15（2.5 を③から出す）を見直す

## NAGARE への反映の仕方（B）
- ⑥のAIは、flow の改善案を NAGARE の**別のブランチ**に出す
- 人が確かめてから取り込む（flow の正本を変えるので、ほかの段の承認と同じく人を通す）

## 記録・考察のAIの動き方
1. ④の実装報告、⑤の検証報告、Andon fail、仕様変更の申し出、物差しの記録を集める
2. AAR の4欄で振り返りの草案を書く（責めない書き方）
3. 不合格を分類ごとに集計し、取り逃がしの段を書く
4. 物差しと各しきい値を確かめ、超えたものを人に上げる
5. 危うかった場面があれば、ヒヤリハットとして提案する
6. 学びを、どこに戻すか（書式・規約・禁止語・分類の判断基準・作業包の大きさ・NAGARE）として案にする
7. 草案 → 出口の条件 → 人の考察と承認 → ②・⑦・NAGARE・EDA へ
